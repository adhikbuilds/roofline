# Data provenance

**Last Updated:** 2026-10-16
**Scope:** Roofline Phase 1 (synthetic seed, ingestion, ground truth)
**Code:** `packages/ingest/src/adapters/synthetic/`, `packages/ingest/src/seed.ts`, `packages/ingest/src/eval/quality.ts`, `packages/db/migrations/0003_ingest.sql`

Roofline v1 contains no real listings. Every listing, unit, price and photo is generated by a seeded program. The five sources are fictional. Nothing is scraped, copied or hot-linked from any portal, and photos are procedural SVG plates rendered by `apps/web/app/img/plate/[seed]/route.ts`.

## 1. Synthetic generator

The generator produces a complete 26-week history for a synthetic Bangalore market, then serves it through the same `SourceAdapter` interface a licensed feed would use.

| File | Responsibility |
|---|---|
| `params.ts` | Every tunable constant: seed, timeline, unit counts, source weights, rent model, defect counts, outcome map |
| `generate.ts` | Builds units, source rows, weekly price versions, planted defects, hard negatives and deals |
| `render.ts` | Turns a `RowSpec` into the raw listing payload (title, prose, rent text, area text, and so on) |
| `rng.ts` | `mulberry32` PRNG plus helpers (`int`, `normal`, `weightedIndex`, `shuffle`, `weightedSample`) |
| `adapter.ts` | `SyntheticAdapter` (one per source). `fetch({ asOf })` is a pure lookup into the pre-generated timeline |
| `truth.ts` | `writeTruth()` writes the ground truth to the `seed_truth` schema |
| `packages/ingest/src/seed.ts` | Orchestrates `pnpm db:seed`: loads reference data, writes ground truth, then runs 26 weekly pipeline runs |

Entry points:

- `pnpm db:seed` (root script; runs `tsx src/cli.ts seed` in `@roofline/ingest`)
- `pnpm db:fresh` = `db:reset` + `db:migrate` + `db:seed`. This is the only supported way to rebuild. `db:seed` refuses to run when synthetic runs already exist.

### Timeline

- 26 weekly runs. `as_of` runs from `2026-04-09T00:00:00Z` (week 0) to `2026-10-01T00:00:00Z` (week 25), in 7-day steps.
- Each week the pipeline ingests only what changed. Listings appear, change price or disappear according to the weekly events below.

### Weekly events

Constants from `params.ts`:

| Event | Constant | Value |
|---|---|---|
| New listings | `WEEKLY_NEW` | 4% |
| Delisting | `WEEKLY_DELIST` | 3% |
| Price change (per live listing per week, after 3+ weeks listed) | `WEEKLY_PRICE_CHANGE` | 2% |
| Price change direction | in `generate.ts` | 80% drop of 3-10%, 20% rise of 3-6% |
| Market drift | `DRIFT_PER_MONTH` | +0.4% per month |

Price changes are never applied to planted defect rows or to genuine deal units. A payload never reverts to a rent it already had.

Source multiplicity: each unit is listed on 1 source (80%), 2 sources (16%) or 3 sources (4%), set by `SOURCE_COUNT_WEIGHTS`. Sources for a unit are chosen without replacement, weighted by the per-kind weights below.

### Units by kind

- Flats: BHK mix 0 (RK) 4%, 1 18%, 2 38%, 3 28%, 4 9%, 5+ 3%.
- Furnishing: unfurnished 30%, semi 45%, furnished 25%.
- PG sources: when choosing sources for a PG unit, `keyloft` (PG weight 0.85) and `doorvale` (PG weight 0.15) are the only eligible sources.
- PG: sharing single / double / triple / quad (`PG_SHARING`), gender male 45% / female 35% / coed 20%, food included 70%.

## 3. The five fictional sources

The generator uses internal keys (`tamarind`, `banyan`, ...). Those keys map onto the public source ids in `packages/db/reference/sources.json`. The public ids and display names are what the database and the UI use. The generator's `SOURCES` table in `params.ts` is the authority.

| Generator key | Source id | Display name | Flat weight | PG weight | Rent skew | Deposit missing | Geo missing | Free-text only |
|---|---|---|---|---|---|---|---|---|
| `tamarind` | `nestlane` | NestLane (demo) | 0.444 | 0 | 1.00 | 8% | 4% | no |
| `banyan` | `rentbarn` | RentBarn (demo) | 0.333 | 0 | 1.00 | 25% | 8% | no |
| `peepal` | `keyloft` | KeyLoft (demo) | 0 | 0.85 | 1.00 | 8% | 5% | no |
| `jacaranda` | `doorvale` | DoorVale (demo) | 0.167 | 0.15 | 1.06 | 8% | 3% | no |
| `gulmohar` | `hearthgrid` | HearthGrid (demo) | 0.056 | 0 | 1.00 | 8% | 25% | yes |

Notes:

- The flat weights sum to 1.0 and the PG weights sum to 1.0. The comment in `params.ts` describes them as shares of rows of that kind. The code applies them per unit when choosing sources.
- `rentSkew` multiplies the observed rent only. DoorVale rows therefore sit about 6% above the ground-truth rent. The `true_rent` table does not include the skew, which is intended: it is a known bias the models should detect.
- `hearthgrid` is the owner-submission source. Its details appear only in the free-text description, which exercises the extraction path in `packages/ingest/src/pipeline/extract.ts`.
- Display names are the five names in `sources.json` (`NestLane`, `RentBarn`, `KeyLoft`, `DoorVale`, `HearthGrid`), each suffixed with "(demo)" by `adapter.ts`. The owner/source descriptions in PLAN.md (for example "Gulmohar Owners") are design notes and are not used in the product.

## 4. Rent model

For a flat (`generate.ts`):

```
base_rent = base2BHK[locality] x BHK_MULT x FURN_MULT x (area / TYP_AREA[bhk])^0.35 x building
```

- `base2BHK[locality]` is `base_2bhk_hint` from `packages/db/reference/localities.json`, defaulting to 35,000 when absent.
- `BHK_MULT`: RK 0.42, 1 0.60, 2 1.00, 3 1.45, 4 2.00, 5+ 2.60.
- `FURN_MULT`: unfurnished 0.90, semi 1.00, furnished 1.18.
- Area: `max(150, round(TYP_AREA[bhk] x (1 + 0.12 x clippedNormal(2.5))))`. `TYP_AREA`: RK 350, 1 600, 2 1100, 3 1550, 4 2300, 5+ 3200.
- `building` = `exp(0.06 x clippedNormal(2))`. This is a per-building effect that neither fair-rent model sees, on purpose.

For PG beds:

```
base_rent = (PG_BASE_SINGLE[zone] x sharing_mult + (food ? 2000 : 0)) x building
```

`PG_BASE_SINGLE` per zone: central 17,000, east 14,000, south_east 14,000, south 12,000, west 11,000, north 12,000, north_east 12,000. Sharing multipliers: single 1.00, double 0.68, triple 0.55, quad 0.48.

Ground truth and observed rents:

- `trueRent = round(base_rent x drift(start_week))`, stored on `seed_truth.units.true_rent_inr`.
- The weekly expected rent is `round(base_rent x drift(w))`, where `drift(w) = (1.004)^(7w / 30.4375)`. It is stored in `seed_truth.true_rent`, one row per unit per live week.
- Each observed row is `round500(trueRent x noise x variant x rentSkew)`, where `noise = exp(0.10 x clippedNormal(2))`. Secondary source rows get a variant factor of U(0.95, 1.05). The primary row uses factor 1.
- Deposits: 60% of rows state a number of months, drawn from 2: 15%, 3: 25%, 5: 25%, 6: 20%, 10: 15%. The other 40% state an absolute amount (months x rent). Deposits are missing at the per-source rate above.

## 5. Ground-truth schema

The ground truth lives in schema `seed_truth`. It is written by `writeTruth()` in a single transaction during `db:seed`.

Access control, from `0001_extensions_roles.sql` and `0003_ingest.sql`:

- `REVOKE ALL ON SCHEMA seed_truth FROM PUBLIC, roofline_app`.
- `REVOKE ALL ON ALL TABLES IN SCHEMA seed_truth FROM PUBLIC, roofline_app`.
- `roofline_app` has no grant on `seed_truth` or `raw_listings`. Evals and the admin role (`withAdmin`) are the only readers.

| Table | Columns | Key | Meaning |
|---|---|---|---|
| `seed_truth.units` | `unit_id uuid`, `locality_id smallint`, `unit_kind` (`rk`, `bhk`, `studio`, `pg_bed`), `bhk smallint`, `area_sqft int`, `furnishing` (`furnished`, `semi`, `unfurnished`), `true_rent_inr int` | `unit_id` | One row per true unit. `true_rent_inr` is the rent at the unit's start week |
| `seed_truth.source_rows` | `source_id text`, `source_listing_id text`, `unit_id uuid`, `defect text` (nullable) | `(source_id, source_listing_id)` | One row per source listing. `defect` is the planted label, or NULL for a clean row |
| `seed_truth.true_rent` | `unit_id uuid`, `as_of timestamptz`, `true_expected_rent_inr int` | `(unit_id, as_of)` | Expected rent per unit per live week |
| `seed_truth.true_deals` | `unit_id uuid`, `kind` (`deal` or `too_good`), `rent_multiplier numeric(4,2)` | `unit_id` | Planted deal and too-good units, with their final multiplier |

The stored `true_deals.rent_multiplier` is authoritative. The too-good multiplier is first set to 0.30, then the outlier audit (section 7) may move it, so do not assume the value is still 0.30. Units that the audit cannot keep as deals are un-planted, so they are absent from `true_deals`.

Indexes: `source_rows_defect_idx` on `defect`, and `source_rows_unit_idx` on `unit_id`.

## 6. Planted defects

Defects are planted by `take()` in `generate.ts`. Each call picks rows from a pool with the seeded PRNG, labels them, and applies a payload change. `take()` throws if it cannot find enough eligible rows, so the counts are exact.

Counts are from `DEFECT_COUNTS` in `params.ts`. Expected pipeline outcome is from `DEFECT_OUTCOME`.

| Defect label | Rows | How it is planted | Expected outcome | Expected warning |
|---|---|---|---|---|
| `rent_one` | 30 | Rent text `₹1` or `1`, week-0 cohort | rejected (`RENT_TOO_LOW`) | none |
| `rent_annual` | 20 | Rent text is 12 x the observed monthly rent, on a dense locality x BHK cell, with the annual figure at most 9 lakh | repaired | `RENT_ANNUAL_REPAIRED` |
| `rent_lakh` | 15 | Rent text written in thousands (rent / 1000, so 42,000 reads as "42"), one per dense cell | repaired | `RENT_UNIT_REPAIRED` |
| `locality_from_nogeo` | 25 | Locality text "From", no geo | rejected (`LOCALITY_UNRESOLVED`) | none |
| `locality_from_geo` | 15 | Locality text "From", valid geo | accepted and flagged | `LOCALITY_FROM_GEO` |
| `locality_bangalore_nogeo` | 9 | Locality text "Bangalore", no geo | rejected (`LOCALITY_UNRESOLVED`) | none |
| `locality_bangalore_geo` | 6 | Locality text "Bangalore", valid geo | accepted and flagged | `LOCALITY_FROM_GEO` |
| `empty_locality_geo` | 20 | Empty locality text, valid geo | accepted and flagged (PostGIS resolves it) | `LOCALITY_FROM_GEO` |
| `furnishing_invalid` | 25 | Furnishing text "11901" | accepted and flagged | `FURNISHING_INVALID` |
| `area_zero` | 8 | Area text "0" | accepted and flagged | `AREA_MISSING` |
| `area_huge` | 7 | Area text "99,999" | rejected (`AREA_IMPLAUSIBLE`) | none |
| `geo_zero` | 10 | Lat/lng both 0 | accepted (geo is not required when locality text resolves) | none |
| `hard_negative` | 150 | See below | accepted | none |
| `too_good` | 10 | Unit rent x 0.30 (then nudged, see section 7), a MAD outlier | rejected (`RENT_OUTLIER_MAD`) | none |

Totals:

- Planted rows the pipeline must reject: `rent_one` 30 + `locality_from_nogeo` 25 + `locality_bangalore_nogeo` 9 + `area_huge` 7 + `too_good` 10 = **81**. This is `PLANTED_REJECT_DEFECTS` in `params.ts`, derived from `DEFECT_OUTCOME`.
- Labelled rows: 190 defects from `DEFECT_COUNTS` (excluding hard negatives), plus 10 `too_good`, plus 150 hard negatives. The hard negatives are not errors: they test that deduplication (Phase 2) does not merge distinct units.

Hard negatives: a distinct unit in the same building, at most 28 m from the anchor (the generator uses `jitterWithin` with radius 28 m), with the same BHK, rent within plus or minus 2% of the anchor's observed rent, a different floor, a different area (plus or minus 2%) and different photos. Each hard negative is a new unit with its own `unit_id`.

Genuine deals: 2% of flat units are targeted (82 survive the audit as `deal` units in the snapshot). They have complete data and rent = truth x U(0.60, 0.78), rounded to 500. These are real deals, not defects, and are used for deal precision and recall in Phase 3. Strictly, a "truth deal" is observed rent at or below 0.80 x true expected rent, which also includes natural noise.

## 7. Audit: only planted rows may be outliers

Before the generator returns, it runs the engine's own outlier test over the week-0 cohort, the way the pipeline runs it:

1. Builds a baseline with `buildBaseline()` from the engine (`packages/engine/src/quality/outliers.ts`).
2. For each natural (non-planted) row, calls `checkOutlier()`. If the row is rejected, its rent is nudged by 6% (up if the z-score is negative, down otherwise) and the test repeats for up to 12 passes. Deal units are lifted by 4%, and if the lift would exceed the top of the deal band (0.78), the deal is cancelled.
3. Pushes too-good rows further down (x 0.90) for up to 6 passes until they are rejected.
4. Throws if any natural row is still an outlier, or any too-good row is not an outlier.

Consequence: the generator can only produce a dataset in which the engine's outlier stage rejects exactly the `too_good` rows. Changing `OUTLIER_PARAMS` or the outlier algorithm in `packages/engine` changes the audit result, which changes the dataset and breaks the snapshot. See section 9.

Weeks 1-25 are audited the same way: new listings and price changes are checked against the prior accepted set, and an outlier is nudged by 6% (up or down, by z-score sign) for up to 10 passes.

## 8. Evaluation

`pnpm --filter @roofline/ingest eval:quality` (the CLI command is `roofline-ingest eval quality`, which needs the admin role and a database) compares pipeline results with `seed_truth.source_rows.defect`. It prints:

```
planted_rejects=<n> matched=<n> extra_rejects=<n> (<pct>% of <rows> rows, limit 1%) total_rejected=<n>
  <defect> expected=<outcome> <asExpected>/<planted>
eval:quality OK | eval:quality FAILED
```

Pass criteria, from `packages/ingest/src/eval/quality.ts`:

- `matched` equals `planted_rejects` (every planted reject is rejected).
- Extra rejects (total rejected minus matched) are at most 1% of all source rows.
- For every defect, the number of rows with the expected outcome equals the number planted. Defects expected to be accepted with a warning must carry the warning listed in the eval (`EXPECTED_WARNING`).

Exit code is 1 when the eval fails.

## 9. Determinism

- One `mulberry32` stream seeded with `SEED = 20261001` (`params.ts`). The generator draws from a single `Rng` in a fixed order, so identical code plus identical reference data gives identical output.
- Unit and listing ids come from `uuidFor(namespace, key)` in `packages/ingest/src/ids.ts`, a SHA-1 derived, version-5-style UUID. No randomness or time is involved.
- `generate.ts` and `adapter.ts` do not call `Date.now`, `Math.random` or `new Date()` (checked by grep). Timestamps are computed from `FIRST_AS_OF` and `WEEK_MS`.
- Content hashes for raw payloads use `stableStringify()` (sorted keys, undefined dropped) before SHA-256, so key order does not change a hash.
- Reference data is read in a fixed order (`ORDER BY slug`, `ORDER BY alias_norm`) before generation.

Tests that enforce it (`packages/ingest/test/generate.test.ts`, `rng.test.ts`):

- Two generations from the same inputs produce identical summaries and identical first 50 rows.
- A different seed (`1`) produces a different summary.
- A snapshot of the first 5 rows and of the aggregates. Any change to the generator, its constants or the engine audit makes this fail. Regenerate the snapshot only after confirming the change is intended.
- Scale and realism bounds: at least 6,400 rows, at least 5,000 units, 26 weeks, 69 localities, plausible PG and flat splits.

Repository-level checks: the `db:fresh` determinism check in PLAN.md Phase 1 compares `md5(string_agg(id::text || rent_inr, ...))` across two runs. It is an acceptance check and has not been recorded as a passing automated test.

Coupling to watch:

- The generator imports `buildBaseline` and `checkOutlier` from `@roofline/engine`. Editing `OUTLIER_PARAMS` (`madFloor`, `zLow`, `zHigh`, `minCellN`, `minIqrN`, `iqrK`, `epsilon`) or the algorithms in `packages/engine/src/quality/outliers.ts` changes the seed. Expect the snapshot and the eval counts to change together.
- Editing `hardRules` bounds (`QUALITY_BOUNDS`) does not change generation, but it changes which planted rows the pipeline rejects, so `eval:quality` may fail.
